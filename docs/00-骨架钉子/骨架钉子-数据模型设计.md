## 一、业务结构（用户亲述，只带一次）

```
两种组织，130+ 个：
  ① 村委会（村）
  ② 社区居委会（社区）
  两种组织的换届选举管理系统，流程大致相同，
  只在「选举细节」和「岗位方式」上有差异。

每个村/社区都有自己的选举日期：
  规则：D = 选举日期（正式选举日）
  业务流 = 从 D 倒排的完整 SOP pipeline

一村搞通，全部复用，只是数据内容不同（社区同理）。

识别关键（防串台）：
  归属地 + 账号 + 密码，缺一不可，不会串台

性质：
  不存在选民！
  这是给「政务组织用户」的基层选举内部系统
```

## 二、最优数据模型（归属地漏斗 · 一套表复用全部）

```
organizations（归属地，130+，顶层隔离）
  id / slug / name / town / type[村|社区] / status
        │  ← 所有业务表都挂 org_id，物理防串台
        ├── accounts（账号）org_id + phone + password + role
        ├── proposals（选举申请/提案）org_id, election_id, prop_status, 审核
        ├── elections（选举活动·每村每届）org_id, el_election_date=D, el_term, el_status, el_proposal_id
        │     ├── election_stages（日程阶段）org_id, election_id, stage_key, start/end_date ← 由D自动生成
        │     ├── positions（岗位·每届）org_id, election_id, pos_name, pos_type, pos_quota
        │     └── candidates（参选人·非选民）org_id, election_id, cand_source[自荐|推荐], 四轮审核
        │           └── materials（材料提交）org_id, candidate_id, 审核
        └── announcements（公告通知）org_id, election_id, 唯一关联 stage, 模板

stage_templates（日程标准模板 = D-day 发动机）
  st_key / st_name / st_day_offset[D-15,D-10...] / st_duration / st_order / org_type[村|社区]
```

**D-day 运转原理**：管理员输入正式选举日 D → 按 org_type 拉取 stage_templates → 用 st_day_offset 计算每个阶段日期 → 生成 election_stages → 公告模板随阶段预填充。

## 四、回归清单（按 PRD 需要改的）

1. **voters(40行) 选民残留** → 冻结不展示，前端无选民入口；参选人一律走 candidates
2. **stage_templates 缺 org_type** → 加 `org_type`(村/社区)，两种组织的模板差异落这里
3. **positions 缺 pos_name** → 加岗位名称；村/社区岗位差异由 pos_type 区分
4. **election_stages 自动生成** → 确认由「D + stage_templates.st_day_offset」自动生成日期（D-day 主链）
5. **归属地漏斗登录** → accounts 必须 org_id + 手机号 + 密码三要素，防串台
6. **公告唯一关系** → announcements 唯一关联 election_stages（不独立乱建）

## 五、铁律

- **org_id 隔离**：所有业务表挂 org_id，一村通村村通，只是数据不同
- **无选民**：candidates 是参选人，voters 是错误残留
- **D-day 唯一**：正式选举日由 elections.el_election_date 定义，日程/公告全部从它推导
- **改结构先改本文件 + PRD，再动代码**

## 六、提案 → 活动 → 岗位 关联规则（业务钉子，2026-08-31 用户亲述）

```
核心链路（数据必须关联，不能断）：
proposals(提案·审批通过) ──1:1──▶ elections(选举活动)
   │                                  │
   │ 提案名称 = 活动名称（原名一致，不做改名/去后缀，可追溯）
   │ 提案的岗位 + 选举方式 ──▶ 侧边栏「岗位管理」中
   │                            「本（提案名称-岗位管理）」明细
   │                                 = 岗位需求 + 资料信息（报名表/资料下载链接）
   │                                 = 小程序前端「选举方式」页展示内容（同一数据源）
   └── 只有提案里确认过的内容可搬；不搬用户管理等其他权限数据（不越界）
```

**钉子规则**：
1. **提案通过即转活动**：审批通过 → 自动生成 elections，**提案名称原样 = 活动名称**
2. **岗位与选举方式下沉**：提案岗位配置 + 选举方式 → 生成岗位管理「本（提案名称-岗位管理）」明细：
   - 岗位需求：岗位名称 / 人数 / 要求
   - 资料信息：报名表、资料下载链接（后台可上传）
3. **小程序数据源**：前端「选举方式」页展示的内容 = 岗位管理明细（同一份数据，不另起炉灶）
4. **唯一关系**：proposals(通过) → elections(1:1) → positions(1:N)；公告/材料/候选人全部挂 elections
5. **不越界**：只搬选举活动相关内容（字段/日期/公告范本/活动排期），用户管理等不搬
