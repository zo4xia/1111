## 一、数据疯狂复用（最高原则）

- **核心思想：数据疯狂复用**——一套表 + 一个 SOP，一村搞通村村复用，只是数据不同（社区同理）
- 130+ 个归属地（村委会 / 社区居委会）共用一套系统，各自独立选举活动
- 归属地漏斗：归属地 → 账号 → 角色 → 事件，缺一不可，防串台
- 前后端都要做：登录页必须选择归属地；做通一个村子的 SOP，其他一模一样 COPY

## 二、核心业务闭环（提案 → 活动 → 岗位 → pipeline）

> **核心认知（用户反复强调）**：**提案确定 → Dday确定 → 小程序前端所有展现内容全部确定**。
> 小程序展示的每一样东西（选举方式、岗位需求、资料下载、日程预告、公告）都是从「提案 + Dday」推导出来的，
> 同一数据源、没有独立内容——小程序前端不自己造数据，只读提案通过后生成的活动数据。

> **分时段展示上线（2026-08-31 用户补充）**：内容确定 ≠ 一次全放。小程序前端是**按 D-day 日程分时段逐步上线**给参选人看的：
> - 已到发布日期的公告/材料窗口 → 对参选人展示
> - 未到日期的（含未来公告、日程预告）→ 对参选人**藏起来**，仅管理侧可见（防提前知道误解）
> - 到什么时间展什么内容，节奏完全由日程 pipeline 驱动

```
提案审批通过
  └─▶ Dday 直接确定（提案选的正式选举日）
        └─▶ 活动列表出现（以「提案名称」命名届）
              └─▶ 点进活动详情
                    └─▶ 所有 pipeline 全部确定：
                         日程(election_stages 按 D 倒排)
                         公告(按日程阶段预填充模板原文)
                         岗位(提案岗位需求 + 资料信息)
                         材料(阶段可开启提交)
```

**钉子规则（2026-08-31 用户亲述）**：
1. **提案通过即转活动**：提案名称原样 = 活动名称（不做改名/去后缀）
2. **岗位与选举方式下沉**：提案岗位配置 + 选举方式 → 岗位管理「本（提案名-岗位管理）」明细（岗位需求 + 资料信息），
   = 小程序前端「选举方式」页展示内容（同一数据源，疯狂复用）
3. **公告唯一关系**：公告发布内容根据日程，唯一关系不乱
4. **不越界**：只搬选举活动相关内容（字段/日期/公告范本/活动排期），用户管理等权限数据不搬

## 三、D-day 运转（日程发动机）

- 先定 Dday（elections.el_election_date）→ 按官方日程模板 stage_templates 的 st_day_offset 倒排生成 election_stages
- 官方模板 16 阶段（本地 PostgreSQL 实查）：
  D-35 前期筹备 / D-34 成立选委会 / D-33~-29 选民登记 / D-28~-24 公示选民名单 /
  D-23~-21 受理选民申诉 / D-20~-16 代表选举 / D-15 候选人提名启动 / D-14 提名延续 /
  D-13 初步候选人汇总+镇级初审 / D-12~-10 竞选预选 / D-9~-5 区级11部门联审党委考察 /
  D-4 正式候选人公示 / D-3~-2 投票竞选筹备 / D-1 投票筹备 / D0 正式投票选举 / D+1~+10 结果备案交接
- 日期 = Dday + offset 天（offset 负为 D 前、0 为 D 日、正为 D 后）

## 四、公告模板库（甲方原版 · 全局复用）

- 第1~17号公告正文模板（公共模板库），村/社区通用（社区 = 村民→居民、村→社区、乡镇→街道 自动替换）
- 管理员只改日期，其他基本不改，只做审批点手指
- 公告按日程阶段自动预填充 → 小编/运营编辑可点开编辑（公文格式实时预览）→ 确认发布
- 公告格式 = 标准公文（标题2号小标宋居中、正文3号仿宋、首行缩进2字符、落款右对齐）

## 五、角色权限

- 漏斗：归属地 → 角色(role) → 关联权限 → 用户(手机号)
- 角色：超管 / 子管理 / 经办编辑 / 审核员 / 参选人
  - 超管、子管理：可编辑可审批；经办编辑：可编辑不可审批；审核员：可审批不可编辑；参选人：查看+提交材料
- 子管理不能创建角色（角色创建超管才行）；子管理可删人员
- 角色切换演示：后台管理 → 角色管理 → 设为当前（localStorage 持久化）

## 六、材料提交（参选人 → 后台审核 → 归档）

- 无选民！参选人 = 面向有资格参选的人（基层民主自荐 + 组织推荐后台导入）
- 自荐需材料审核通过后与候选人走一起；组织推荐（后台手工导入）不用材料审核
- 阶段可「开启材料提交」→ 用户端公告下显示提交按钮 → 上传材料进材料管理 → 归档历史归档本届文件夹

## 七、小程序端最终定义（2026-08-31 用户亲口明确 · 脱稿制）

> 小程序端本质就三件事：**展示 + 收集材料 + 看最近通知，没有别的**。

### 7.1 提案审批通过那一刻，小程序端立即全部确定（静态数据，一次到位）
1. **首页**：Dday（正式选举日）确认并显示
2. **公告通知页**：活动预告（**灰色 = 未到日期的未来步骤**）全部有数据
3. **公告内容**：全部有数据模板（第 1~17 号公告模板预填充，村/社区通用）
4. **首页金刚区 → 选举方式**：点进去的**岗位 + 选举说明**全部内容都有了（数据源 = 岗位管理明细）

### 7.2 动态变化的内容（跟着日程时间表驱动，到点才解锁/变化）
1. **最新公告**：跟着时间日期逐个变成可阅读、可点击查看（未到日期的灰色/隐藏）
2. **提交材料**：材料提交窗口按日程到点开/关
3. **候选人提名情况展示**：四轮审核结果随时间推进更新
> 以上三者都跟着时间表（election_stages）走，没有独立逻辑。

### 7.3 复用规则（村/社区）
- 不同村子**进度、内容不一样**（各自 Dday、各自数据），但**本质业务 pipeline 一毛一样**
- **村子同类、社区同类**（村与村完全复用，社区与社区完全复用）
- **村子和社区不一样的只有几个小地方**（选举方式、岗位细节差异），差异落在 org_type + stage_templates/positions，不单独做页面

### 7.4 活动详情时间轴 UI 要求（2026-08-31 截图标注，脱稿制）
- **阶段状态三色**（按当前日期相对阶段日期判断）：
  - 当前进度所在阶段 → **红色底色**高亮
  - 已经走过的阶段 → **浅浅的绿色**
  - 还没开始的阶段 → **浅灰色**
- **每个阶段都要给编辑经办/运营留操作位**（不能只展示）：发布公告、查看已上传材料、更新候选人展示 等按钮，按阶段类型出现
- 时间轴当前已含字段：核心工作 / 系统动作 / 关联公告（可点查看）/ 材料类型

## 九、封地治理框架（2026-09-02 用户亲授 · 项目记忆方法论）

> **核心隐喻**：项目=国家，功能模块=封地。良好的国王协调各封地商贸往来清晰（业务流=商贸线路），每个封地有独一无二的作用（唯一性，不是唯一就会挤兑乱价=两个真相）。

**每个封地的小领主（agent）必须喊清三句话**：
1. **我是干嘛的**（唯一性定位：这个模块干什么，不跟别的重复）
2. **我供应啥**（出参：字段/参数/业务流，我能给下游什么）
3. **我缺啥**（入参：我需要上游给我什么）

三句话喊清楚，需求自动匹配，大家一看就知道自己找哪个领主。

**落地文档**：`docs/00-骨架钉子/封地契约-模块边界与接口.md`（9个封地+领主制+商贸线总图+唯一性检查清单）

**改代码前的强制流程**：
1. 先读封地契约，确认这个功能属于哪个封地
2. 检查有没有其他封地也在做同样的事（有→合并，留唯一入口）
3. 改完更新该封地的"供应啥/缺啥"
4. 下游封地的入参变了，通知下游领主
