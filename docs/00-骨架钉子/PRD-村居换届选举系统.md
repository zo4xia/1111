# 村居换届选举系统 · 产品需求文档（PRD）

> 版本：v1.0 ｜ 日期：2026-08-31 ｜ 状态：业务真相对齐版
> 本文档是系统的**唯一业务基准**。任何实现细节冲突时，以本文档为准。

---

## 0. 系统最终定义（傻瓜式 · 四件事）

**系统 = 日程 pipeline + 材料收集 + 公告自动提示 + 审核公示，傻瓜式。**

| # | 系统做的事 | 说明 |
|---|---|---|
| 1 | **日程 pipeline** | D-day 自动倒排的换届日程，一路走到投票日 |
| 2 | **材料收集** | 前端提交/收集参选人材料 |
| 3 | **公告自动提示** | 公告跟随日程，**提前自动提示管理员"该发公告了"**；管理员登录确认无误 → 点发布 |
| 4 | **审核 + 公示** | 材料审核 + 选举期间**四轮审核结果公示**（后台审批、查看材料） |

**系统不做的**：不登记选民、不投票、不受理申诉——那些是领导们/政务人员线下做的政务工作。系统只是**告诉管理员每个阶段该做什么、该发什么公告**（傻瓜式：打开系统就知道今天该干嘛）。

---

## 0.2 前端范围（傻瓜式六模块 · 唯一有的）

| # | 前端模块 | 说明 |
|---|---|---|
| 1 | **材料提交** | 参选人/候选人提交材料 |
| 2 | **候选人选举情况展示** | 一轮/二轮/三轮/四轮审核结果公示 |
| 3 | **日程预告** | D-day 倒排日程 pipeline，告诉用户今天该干嘛 |
| 4 | **公告按日期发布** | 公告跟随日程，按日期发布 |
| 5 | **选举岗位要求说明** | 岗位要求展示 |
| 6 | **资料下载** | 资料下载区 |

**前端就这六个模块，没有别的**（无选民端、无投票、无复杂权限界面）。

**系统形态 = 纯官宣平台**：像政务官网的换届专栏——前端把日程/公告/候选人公示/岗位说明/资料下载作为"官宣内容"展示给所有人看；唯一交互是材料提交；后台由管理员审核材料、确认发布公告、更新公示。傻瓜式，打开即知。

---

## 0.3 复用铁律（最重要 · 一村通村村通）

**每个村子都是这样的（同一种官宣模式），一个搞定，其他都搞定。**

- 所有村/社区 = 同一套系统、同一套流程、同一套页面、同一套模板
- 差异只有两处：① 数据内容（org_id 区分）② 村/社区的类型差异（选举细节 + 岗位方式）
- **做好一个村的完整样例 → 其他 130+ 个全部复用，只是数据不同**
- 不许为某个村单独开发、单独定制页面

---

## 0.4 权限模型（参选人 vs 管理侧 · 用户钦定）

**两侧**：超管 / 管理（子管理） / 经办编辑 = 管理侧（有操作权）；参选人 = 前端展示（无操作权）。

**参选人看不到（前端直接隐藏按钮，不是置灰）**：

| # | 操作 | 参选人 |
|---|---|---|
| 1 | 编辑公告 | ✗ 无按钮 |
| 2 | 确认发布公告 | ✗ 无按钮 |
| 3 | 查看已提交的用户材料 | ✗ 无按钮 |
| 4 | 编辑候选人展示的最新结果 | ✗ 无按钮 |

**按日期隐藏（重要）**：日期没到的公告和通知，参选人**看不到（藏起来）**——只展示已到发布日期的内容；未来的公告/预告仅管理侧可见。

**参选人全部能力（就这些，没了）**：

| # | 参选人能做的 |
|---|---|
| 1 | 提交材料（上传内容） |
| 2 | 下载每次公告 |
| 3 | 下载报名表 |

> 参选人 = 纯提交 + 下载。其余任何操作（编辑/发布/审核/看用户材料/改结果）一律无按钮。

## 0.5 一句话定位

**一套给"基层选举内部工作人员"用的换届选举管理系统。**
不是给选民投票的系统，**不存在选民**。系统服务的对象是：政务组织用户（选委会、村干部、镇街干部等），做的是"组织选举、管材料、发公告、走流程"的内部事务。

## 1. 核心业务真相（不可动摇的钉子）

| # | 真相 | 说明 |
|---|---|---|
| 1 | **两种组织** | ①村委会（村）②社区居委会（社区），合计 **130+ 个** |
| 2 | **流程同构** | 村和社区的换届流程大致相同，只有**选举细节**和**岗位方式**有差异 |
| 3 | **每村独立** | 每个村/社区都有自己的**选举日期**，互不干扰 |
| 4 | **D-day 规则** | **D = 正式选举日**。整个业务流是从 D 倒排的完整 SOP pipeline |
| 5 | **一村通、村村通** | 一个村/社区跑通整个 pipeline，其他全部复用，**只是数据内容不同** |
| 6 | **三要素防串台** | 登录识别 = **归属地 + 账号 + 密码**，缺一不可 → 130 个组织各管各的，绝不串台 |
| 7 | **漏斗式架构** | 归属地 → 组织类型（村委会/社区居委会）→ 角色权限 → 账号（手机号）→ 所有业务事件 |
| 8 | **无选民** | 没有选民登记/投票环节；面向的是"有资格参选的人 + 组织管理的人" |
| 9 | **内部系统** | 参选人 = 基层民主自荐（需材料审核）；另有组织推荐/后台导入（免材料审核） |

## 2. 系统架构原则

### 2.1 漏斗式数据隔离（最关键）

```
最高层：归属地（村 / 社区，130+ 个）
   ↓
组织类型：村委会 ｜ 社区居委会
   ↓
角色：平台超管 / 子管理（村/社区管理员）/ 业务角色
   ↓
账号：手机号 + 密码（首次登录绑定归属地）
   ↓
业务事件：选举活动、材料提交、候选人审批、公告通知、日程执行
```

- **归属地在最顶层**：没有归属地就没有账号、没有业务。
- 归属地选错，账号密码对了也进不去 → 天然隔离，不会串台。
- 每个村/社区的数据表是独立的（各自进度、各自 D-day、各自岗位）。

### 2.2 复用原则

- 做好**一个村/社区**的完整 SOP，其他 130+ 全部 copy 复用，只换数据。
- 前端页面、后端接口、数据库表结构**全量复用**。
- 数据按 `org_id`（归属地）隔离。

## 3. 登录与账号体系

| 项 | 规则 |
|---|---|
| 登录三要素 | **归属地 + 账号（手机号）+ 密码**，缺一不可 |
| 首次注册 | 必须先选归属地，再输入手机号+密码 → 直接绑定归属地 |
| 串台防护 | 归属地不对，账号密码正确也无法登录 |
| 微信授权 | 暂缓（"微信授权登陆再说"），当前用手机号+密码 |
| 角色 | 平台超管 / 子管理（各归属地管理员）/ 业务角色（操作员/审核员等） |

**子管理权限边界**：
- 子管理：可增删**人员**，管理本归属地业务。
- 子管理：**不能**创建/删除**角色**（角色定义是超管权限，前端用 isAdmin 判断隐藏）。

## 4. 换届选举业务流（D-day 倒排 pipeline）

> D = 正式选举日（由管理员在前端输入）。一旦输入 D，整套日程自动按 SOP 流转。

```
① 选举申请（提案 proposals）
   ├─ 历届选举记录（本村/居历史，prop_status=通过 的最新一条 → 当前活动）
   ├─ 提交选举申请材料（弹窗编辑 + 附件上传）
   └─ 审核（通过后才进入下一步）
      ↓
② 创建选举活动（elections）
   ├─ 设置 el_election_date = 正式选举日 D（关键）
   ├─ 关联 elections ↔ election_stages（双相关联）
   └─ 审核通过的申请才能创建活动
      ↓
③ 日程/阶段生成（election_stages + stage_templates）
   ├─ 确认 D-day 后，按组织类型（村/社区）自动生成倒排日程
   ├─ 每阶段带公告预填充模板（stage_templates）
   └─ 日程表 at_code 列与模板对应
      ↓
④ 岗位管理（positions）
   ├─ 关联每一届选举活动（每届岗位数不同）
   └─ 区分村/社区岗位方式差异
      ↓
⑤ 参选人报名（candidates 参选人，非选民）
   ├─ 自荐：提交材料 → 材料审核 → 通过后进入候选池
   ├─ 组织推荐/后台导入：直接入池，免材料审核
   └─ 材料提交人 = 参选人本人（materials 表）
      ↓
⑥ 候选人审批（proposals/approvals）
      ↓
⑦ 公告通知（announcements + announcement_templates）
   ├─ 公告内容严格跟随日程（唯一关系，不乱建）
   └─ 模板库按日程节点预填充
      ↓
⑧ 选举执行 → 结果归档（archives / election_results）
```

### 4.1 关键机制：日期自动计算

- 管理员在**前端**输入正式选举日 D → 系统自动倒推整个 `election_stages` 日程表。
- 每个阶段的日期 = D - 倒排天数（如 D-15、D-10、D-5 等）。
- 演示口径：以 D = 2026-10-30 为样例验证计算。

## 5. 两种组织差异（村 vs 社区）

| 维度 | 村委会 | 社区居委会 |
|---|---|---|
| 选举流程 | 大致相同 | 大致相同（同 pipeline） |
| 选举细节 | 按村规 | 按居规，细节有差异 |
| 岗位设置 | 村委会岗位 | 居委会岗位（如主任/副主任/委员，比例不同） |
| 日程模板 | stage_templates 按组织类型区分 | 同左 |
| 数据隔离 | org_id 独立 | org_id 独立 |

> 差异点收敛在**岗位方式**和**选举细节**两处，其余全复用。

## 7. 数据表核心映射（本地 PostgreSQL）

| 表 | 业务含义 | 关键字段 |
|---|---|---|
| organizations | 归属地（村/社区，130+） | slug, name, 类型(村/社区) |
| accounts | 账号 | acc_phone, acc_password, org_id, acc_status |
| roles / account_roles | 角色及分配 | role_key, scope(platform/organization), permissions |
| proposals | 选举申请（提案） | prop_status, 历届记录, 附件 |
| elections | 选举活动 | el_election_date(D), el_term, el_status, org_id |
| election_stages | 日程阶段 | 与 elections 双相关联, at_code, 倒排日期 |
| stage_templates | 日程标准模板 | 按组织类型, 公告预填充 |
| positions | 岗位 | 关联 elections, 村/社区差异 |
| candidates | 参选人（非选民） | org_id, election_id, 状态, 来源(self/org_recommend) |
| materials | 材料提交 | mat_candidate_id, mat_submitter(参选人), 审核状态 |
| announcements | 公告通知 | 唯一关联日程 |
| announcement_templates | 公告模板库 | 按日程节点 |
| archives / election_results | 归档/结果 | 备案/交接状态 |
