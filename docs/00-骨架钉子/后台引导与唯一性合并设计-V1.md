## 2. 唯一性合并 · 目标形态（结合你两个喜好）

你喜欢的两个点：
1. **公告管理里每份公告清清楚楚**（逐条、各自附件、各自状态）
2. **小编工作台的编辑内容 + 发布方式模块 + 公文切换**（好用）

**合并后的目标形态（单一真相，不再两处编辑）：**

```
┌────────────────────────────────────────────────────────────────┐
│  写入口（唯一）               小编工作台 ActivityDetail          │
│   每阶段：选公告(Radio切换) → 编辑正文/落款/成文日期              │
│           → 传本公告附件(独立) → 开材料开关 → 立即/定时发布       │
│           → 存草稿/预览公文(NoticeDoc)                          │
└───────────────────────────┬────────────────────────────────────┘
                            │ 写 → announcements 表 + uploads/announcements/<id>/
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  只读台账（公告记录页）                                          │
│   每行=一份公告：号/标题/阶段/附件份数/发布日期/状态              │
│   操作：查看(NoticeDoc+该公告附件) / 去工作台编辑 / 发布          │
│   —— 不再有任何「编辑正文」入口                                  │
└───────────────────────────┬────────────────────────────────────┘
                            │ 读
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  消费端（小程序 notice 页）                                      │
│   公告列表 → 详情：正文 + 【本公告附件列表(切换公告随之切换)】      │
│   —— 只读，无编辑                                              │
└────────────────────────────────────────────────────────────────┘
```

**验收（违背任一条=没做完）：**
1. 公告记录页不存在任何「编辑正文」表单；编辑只能通过「去工作台编辑」跳转。
2. 同一份公告在小程序、公告记录、小编工作台预览的**正文/落款/附件长相一致**。
3. 小程序切换公告 → 该公告附件列表随之切换（不再写死/死链）。
4. 小编工作台编辑的**每个字段都真落库**（刷新不丢），附件真上传到该公告独立目录。

## 3. 后台气泡引导（首次使用引导）

> 目标：让各村/社区经办第一次进后台就知道「先做啥、在哪做」，减少下午出错。

### 3.1 引导流程（登录后按步骤浮现）

```
登录成功
  └─▶ 第 1 步：确认归属地
        "请先确认你的村/社区：你登录的归属地 = 华亭镇·涧口社区居委会。
         本系统所有数据（公告/岗位/材料）都只属于这一个村/社区。"
  └─▶ 第 2 步：如果本届还没建
        "先去「提案审批」新建提案：填正式选举日(D) + 岗位信息 + 详细说明 → 提交审核。
         （公告原文由模板库自动生成，小编在工作台改日期/正文即可，提案不用传公告文档）"
  └─▶ 第 3 步：审核通过后
        "系统已自动生成：16 阶段日程 + 公告草稿 + 岗位需求。
         去「活动列表」点进本届 → 左侧时间轴点阶段 → 右侧「小编工作台」编辑发布公告。"
  └─▶ 第 4 步：到点回填
        "材料审核 / 候选人管理：到时间由甲方线下审核后回填结果，普通页面只读展示，不用你在上面编辑内容。"
  └─▶ 结束：提示可「不再显示」，或在帮助中心随时重看
```

### 3.2 实现建议

- 登录后首页（Dashboard/Home）顶层浮层，步骤条驱动，每步配截图/高亮锚点（可定位到对应菜单）。
- 按钮：上一步/下一步/跳过（暂不显示）/不再显示（localStorage 持久化）。
- 首次进入 + 该归属地「本届尚未创建提案」时才弹全流程；已有提案则只弹第 3/4 步。
- 技术选型：自研轻量 Step 组件即可（TDesign 有 Guide/Steps 组件可用，避免引新依赖）。

## 5. 选举创建流程（提案 → 审核 → 自动生成 → 分时段解锁）

> 已在 D-002 实现「审批通过一个事务内联动生成」。本节把它写成操作者视角的规范流程 + 补上「公告文档文件」细节。

```
【经办/子管理】新建提案
   ├─ 填 正式选举日期（D 日）              ← 唯一锚点，之后全部由 D 倒排
   ├─ 填 换届选举岗位信息（岗位行：岗位名+人数+要求）
   └─ 填 详细说明
        （公告原文由模板库自动生成 18 条草稿，小编在工作台改日期/正文/落款即可，
          提案不用上传公告文档；正式公文=公告记录里 NoticeDoc 预览的样子）
        │
        ▼ 提交提案（状态 pending）
【审核员/超管】提案审批 → 点「通过」
        │
        ▼ 系统事务内自动完成（一次点击，全部生成）
   ├─ 锚定 D 日 → elections.el_election_date
   ├─ 按归属地 org_type（村/社区）生成 16 阶段日程（D-35 → D+10 倒排）
   ├─ 预填充 18 条公告草稿（draft，公告模板库原文）
   ├─ 填充 本届岗位需求记录
   └─ 落示意附件（真实物料优先，缺则纯文本占位）
        │
        ▼
【小程序端同步】
   ├─ 日期没到的公告 → 灰度/隐藏（未解锁，防提前误解）
   ├─ 到日期的公告 → 解锁可见、可下载附件
   ├─ 材料窗口到点自动开关
   └─ 候选人公示四轮审核结果随日程推进更新
```

**验收点：**
1. 审核通过后，活动列表立刻出现以「提案名称」命名的新届，16 阶段/18 草稿/岗位数一次到位（D-002 已验证）。
2. 重复点击「通过」被 400 拦截（原子抢占）。
3. 同一个提案改 D 日后重审 → 日程整体重算（shiftDate 纯日期，无 UTC 偏移）。

## 7. 归档目录结构（钉死 · 用户要求）

> 用户原文：「服务器端什么村什么届什么分类文件夹，下面一个用户提交就用这个用户的名称-竞选岗位 上传时间来存档。后台的档案文档归档和材料管理、候选人管理里面，所有的选举材料的预览点击审核都在这里文件夹，重要！」

### 7.1 目标结构（2026-09-02 已确认命名格式 · 按数据库字段取）

> 命名格式：`归属地(村/社区) - 届 - 提交时间 - 竞选岗位 - 提交人`，每个字段都从数据库取（org.name / election.term / materials.mat_submit_time / position / applicant name），不手填。

```
backend/uploads/                    （静态服务 /api/files/ 根）
└─ materials/                       材料归档（= 材料管理/候选人管理/档案预览审核的真源）
   └─ <归属地>/                      村或社区中文名，如 涧口社区居委会
      └─ <届名>/                     如 第十届换届
         └─ <分类>/                  材料分类（沿用 kit 的 MATERIAL_TYPES 单一真相）
            └─ <归属地>-<届>-<提交时间>-<竞选岗位>-<提交人>/
               例：涧口社区居委会-第十届-20260715-主任-张三/
               ├─ 身份证.jpg
               ├─ 自荐表.pdf
               └─ 无犯罪证明.pdf
```

### 7.2 与现状的差异与改法

| 现状 | 目标 | 改法 |
|---|---|---|
| `uploads/<材料id>/`（DB 主键目录，可读性差） | `uploads/materials/<归属地>/<届>/<分类>/<归属地>-<届>-<时间>-<岗位>-<提交人>/` | 材料上传路由改为按 DB 字段拼目录名；DB 的 materials 行记录目录路径（或仍按目录扫描，保留 D-010 无第二列原则） |
| 材料管理/候选人管理预览 | 预览/审核都指向该归档目录的真实文件 | 读目录扫描结果渲染；审核通过=标记状态，文件不动（不复制，避免第二真相） |
| 历史归档 Archives | 已审核归档在本届文件夹 | 归档=状态置为已归档 + 目录保留，不搬文件 |

### 7.3 注意（防踩坑）
- 目录命名用**归属地 slug + 届名（含中文）**，注意 Windows/服务器文件系统对中文的支持；建议统一 URL 编码规则。
- 严禁把同一份材料复制到两个目录（= 第二真相，违背唯一性）。
- 目录即档案：删除材料 = 从 DB 移除记录 + 清目录，要谨慎（可标记删除而非物理删）。

### 9.3 流程（参选人视角）

```
点岗位「提交材料」
  → 弹窗显示该岗位所需材料清单（每种带「下载模板」）
  → 参选人下载模板 → 线下填写/准备
  → 切到对应材料类型 tab → 拍照/选文件上传
  → 可加备注 → 提交
  → 后端落库 + 归档到 §7 目录（归属地-届-时间-岗位-提交人）
  → 「我的提交记录」实时显示状态（待审/审核中/通过/驳回）
  → 审核结果通过小程序「我的通知」推送
```

### 9.4 关键设计点

| 点 | 规则 |
|---|---|
| 按岗位分 | 每个岗位独立的材料提交入口，材料清单可按岗位配置（主任/副主任/委员所需材料可能不同） |
| 模板下载 | 每种材料都有「下载模板」按钮，模板文件由后台上传到 `uploads/material_templates/`，参选人下载后填写 |
| 按材料类型分 tab | 身份证/自荐表/无犯罪证明 各一个 tab，每种单独上传，避免混在一起分不清 |
| 归档目录 | 提交后按 §7 结构归档：`归属地-届-时间-岗位-提交人/`，每种材料一个文件 |
| 状态回流 | 审核通过/驳回 → 小程序「我的提交记录」+「我的通知」同步更新 |
| 材料窗口 | 仍受日程引擎控制（D-15~D-13 窗口），窗口外按钮置灰并提示 |

### 9.5 与后端的接口约定（待核查 agent 确认现有接口是否够用）

- `GET /api/positions` → 岗位列表 + 每岗位所需材料类型
- `GET /api/materials/templates/:type` → 下载该材料类型的模板文件
- `POST /api/materials` → 创建材料记录（带 positionId + matType）
- `POST /api/materials/:id/upload` → 上传该材料类型的文件（归档到 §7 目录）
- `GET /api/mp/materials/mine` → 我的提交记录（含状态）
