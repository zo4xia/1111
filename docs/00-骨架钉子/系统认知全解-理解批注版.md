# 村居换届选举系统 · 认知全解（理解批注版）

> 2026-08-31 定稿 · 每条含「理解批注」：为什么这样 / 怎么运转 / 防什么坑
> 本文档 = 团队共同理解基准，开工时逐条对照

---

## 一、系统定位

**一句话：一套给基层选举内部人员用的换届官宣系统——登录进村，看日程，管理侧操作、参选人提交下载。**

- **理解批注**：这不是给老百姓投票的系统，是给"组织选举的人"（村干部/选委会/镇街干部）用的**内部工作台**。所以它天然没有选民端、没有投票、没有申诉——那些是政务人员线下做的事，系统不越权。系统只做四件事：日程 pipeline、材料收集、公告提示、审核公示。
- **为什么傻瓜式**：用户是基层工作人员，可能年纪大、怕复杂。系统要让他们"打开就知道今天该干嘛"，所以一切靠日程自动流转 + 提前提醒，不让他们记流程、不开人工开关。

## 二、复用铁律

**每个村子都是这样，一个搞定，其他都搞定。**

- **理解批注**：130+ 个村/社区，不可能逐个开发。核心洞察 = **流程完全一样，只有数据不同**。所以系统做成"一套模板 + 数据隔离"：org_id 区分归属地，一个村跑通 = 所有村跑通。**禁止为任何村单独定制页面**——那是自杀式做法。
- **防什么坑**：千万不要因为"某村特殊"就加特殊逻辑，一加就破坏复用性。

## 三、登录漏斗（防串台）

**归属地 → 组织类型（村/社区）→ 账号（手机号+密码）→ 角色 → 进自己的村**

- **理解批注**：归属地是**第一道也是最大的一道过滤**。130+ 个村数据全在一个库里，最怕"串台"（A 村看到 B 村数据）。漏斗式设计 = 先锁定归属地，再验证账号，层层收窄。归属地不对，账号密码对了也没用。
- **为什么缺一不可**：归属地决定数据范围，账号决定身份，角色决定权限。三者组合才构成一个合法的"村里人"。

## 四、角色与权限

| 角色 | 定位 | 能力 |
|---|---|---|
| 参选人 | 纯展示 | **就三件事**：提交材料、下载公告、下载报名表。**没了** |
| 管理侧（超管/子管理/经办编辑） | 操作 | 六模块全功能 + 编辑/发布公告 + 看用户材料 + 审核 + 改候选人结果 |

- **理解批注**：参选人**无权限不是"置灰"，是"不渲染按钮"**——前端直接不显示，不给"看得到点不了"的挫败感。同时后端接口也要校验（**前端隐藏 + 后端拦截双保险**，光藏按钮没用，直接调接口还是能访问）。
- **按日期隐藏**：参选人只看到**已到发布日期**的公告/通知，未来的（含管理侧能看到的预告）**藏起来**。这符合真实政务场景——没到时间的事不该让参选人提前知道，防止误解。
- **防什么坑**：权限判断不能只靠前端，后端每个接口都要带角色校验，否则绕过前端照样拿数据。

## 五、前端六模块（小程序蓝本 · 青墨鎏金克制版）

管理侧：① 首页（进度一目了然）② 公告通知（三Tab+阶段分组+红头详情）③ 候选人公示（四轮轨迹）④ 材料提交（窗口自动开关）⑤ 选举流程/岗位 ⑥ 我的。
参选人：材料提交 + 公告下载 + 报名表下载。

- **理解批注**：前端本质 = **官宣展示页**，像政务官网换届专栏。信息是"展示给人看"的，不是给人操作的。所以风格要**朴素稳重、信息优先、装饰克制、公文质感**（仿宋正文、红头分割线、盖章），标杆 = 首页 + 公告通知列表。
- **为什么禁止花哨**：政务系统要的是可信、稳重。hero 大渐变、光晕、夸张动画会让人"飘"，失去官宣的严肃感。
- **防什么坑**：别把前端做成"管理后台"那种一堆按钮密密麻麻的样子；它是给参选人看的干净公开展示 + 给管理员用的简单工作台。

## 六、提案审批（Dday 的源头）

**后台第一个模块**。编辑/经办/子管理提交「选举申请方案」→ 审核 → 通过/驳回。

提交内容：① 选举日期（D）② **选举方式（村/居委会有差别）★** ③ 岗位配置（岗位+人数+要求）④ 岗位报名表/资料表下载链接。

- **理解批注**：**D 不是拍脑袋定的，是走审批流程确定的**。这是严谨的政务逻辑：举办选举要申请、要批准，批了才生效。**通过 = 三样一起锁定**：D 确认 + 前端选举方式确定 + 后台岗位内容确定。锁死之后这套配置就固定了，不会乱。
- **为什么有「选举方式」列**：村（村委会）和居委会（社区居委会）的**选举方式不一样**（选举细节、岗位方式有差异）。提案里必须声明用哪种方式，通过后前端展示的、后台执行的都是这一种。
- **防什么坑**：驳回 = 不行，可修改重提；通过的最新提案才是当前活动，历史提案只是记录（归档查看）。

## 七、日程引擎（发动机 · 唯一时钟）

```
D（正式选举日）→ 读 stage_templates（16 阶段偏移量）→ 生成 election_stages（每阶段真实日期）
```

- **理解批注**：这是全系统的心脏。**只存"模板偏移量 + D"，不存死日期**——改 D 全表平移重算。16 阶段的"相对 D 的偏移"是固定的（比如 D-35 公告、D-15 材料上报…），D 定了，所有真实日期自动算出来。
- **为什么这样设计**：130+ 个村 D 各不相同，但流程相同。用"偏移模板" = 一套模板复用所有村，改 D 就自动生成该村日程。这正好呼应复用铁律。
- **防什么坑**：日期计算必须用**数据库函数/后端统一算**，前端只展示，不自己算，避免口径不一致。

## 八、日程驱动执行（无人工开关 + 防遗忘）

**一切动作按日程自动执行**：报名窗口到点开/关、材料上传窗口到点开/关、审核时间到点、公告跟随日程。

- **理解批注**：**系统不做任何人工开关**——窗口自动开、自动关。管理员的职责 = **跟着日程提示走**：该发公告就确认发，该审核就审。
- **防遗忘提醒（核心价值）**：管理员/工作人员**很怕自己忘记**，所以系统在阶段开始前**提前提醒**"该做 X 了"（发公告/收材料/审核…）。**公告自动提示 = 给工作人员敲钟**，不是给群众看的。
- **近期预告 = 还没开展的步骤**：前端公告通知的「预告」Tab 把未来未开展的日程步骤列出来，管理员一眼看到接下来要做什么；但**对参选人隐藏**。
- **防什么坑**：提醒要"提前"（阶段开始前 N 天提醒），不是当天才提醒；预告和管理员待办要清晰区分。

## 九、公告按日期发布

- **理解批注**：公告跟着日程走，**每个阶段对应一份公告**（由公告模板预填充正文），到点发布。参选人只看到已到发布日期的；未来的预告仅管理侧可见。发布 = 管理员确认（不是自动发），**确认动作是人工的，窗口开关是自动的**——一个管"发不发"（人工），一个管"能不能收"（自动）。
- **防什么坑**：公告正文用公告模板预填充，管理员只需核对确认，减少手打错误。

## 十、材料审核（四轮公示）

```
参选人提交 → 管理侧查看审核 → 四轮审核结果公示
r1 材料收审 → r2 资格审核 → r3 资格复核 → r4 最终确认（前置不过后续冻结）
```

- **理解批注**：四轮是**递进关系**，前面不过后面全部冻结（不是平行审核）。公示结果 = 候选人页展示的"一轮/二轮/三轮/四轮"轨迹。参选人提交的材料管理侧可查看审核，参选人自己看不到别人的材料。
- **防什么坑**：审核记录要留痕（审核人、时间、意见），四轮状态要可回溯。

## 十一、后端架构

**PostgreSQL（23 表已建）+ Node/Express + JWT + 本地文件存储**

- **理解批注**：JWT 里带 org_id + role，**所有查询强制 org_id 过滤** = 数据隔离的落地手段（防串台的技术实现）。参选人 API 只暴露三个（提交材料/下载公告/下载报名表），管理侧接口单独权限。
- **为什么轻量**：系统不复杂，不需要重型框架。稳定 > 炫技。数据库已本地跑通，后端用熟悉的技术栈快速落地。
- **防什么坑**：文件上传做类型/大小校验；登录失败要区分"归属地错/账号错/密码错/无角色"。

## 十二、最新业务钉子（2026-08-31 补录 · 数据疯狂复用）

### 12.1 数据疯狂复用（最高原则）

- **核心思想：数据疯狂复用**——一套表 + 一个 SOP，一村搞通村村复用，只是数据不同（社区同理）。
- 130+ 归属地（村委会 / 社区居委会）共用一套系统，各自独立选举活动；归属地漏斗（归属地 → 账号 → 角色 → 事件）防串台。
- **理解批注**：任何模块做通一个村 = 全量复用。禁止为任何村/社区单独定制逻辑或页面，一加就破坏复用性。

### 12.2 核心业务闭环（提案 → 活动 → 岗位 → pipeline）

```
提案审批通过
  └─▶ Dday 直接确定（提案选的正式选举日）
        └─▶ 活动列表出现（以「提案名称」命名届）
              └─▶ 点进活动详情
                    └─▶ 所有 pipeline 全部确定：
                         日程(election_stages 按 D 倒排)
                         公告(按日程阶段预填充模板原文)
                         岗位(提案岗位需求 + 资料信息)
                         材料(阶段可开启提交)
```

**钉子规则**：
1. **提案通过即转活动**：提案名称原样 = 活动名称（不做改名/去后缀，可追溯）
2. **岗位与选举方式下沉**：提案岗位配置 + 选举方式 → 岗位管理「本（提案名-岗位管理）」明细（岗位需求 + 资料信息）
   = **小程序前端「选举方式」页展示内容（同一数据源，疯狂复用，不另起炉灶）**
3. **公告唯一关系**：公告发布内容根据日程（stage → 公告模板），唯一关联不乱
4. **不越界**：只搬选举活动相关内容（字段/日期/公告范本/活动排期），用户管理等权限数据不搬

### 12.3 D-day 运转（日程发动机 · 官方模板 16 阶段）

- 先定 Dday（elections.el_election_date）→ 按官方日程模板 stage_templates 的 `st_day_offset` 倒排生成 election_stages
- **官方 16 阶段**（本地 PostgreSQL 实查，村/社区共用同一流程）：
  D-35 前期筹备 / D-34 成立选委会 / D-33~-29 选民登记 / D-28~-24 公示选民名单 /
  D-23~-21 受理选民申诉 / D-20~-16 代表选举 / D-15 候选人提名启动 / D-14 提名延续 /
  D-13 初步候选人汇总+镇级初审 / D-12~-10 竞选预选 / D-9~-5 区级11部门联审·党委考察 /
  D-4 正式候选人公示 / D-3~-2 投票竞选筹备 / D-1 投票筹备 / D0 正式投票选举 / D+1~+10 结果备案·新旧班子交接
- **日期 = Dday + offset 天**（offset 负为 D 前、0 为 D 日、正为 D 后）；前端只展示，统一由生成逻辑算，避免口径不一致
- 每阶段含：核心工作 / 系统动作 / 关联公告 / 审核轮次 / 材料类型

### 12.4 公告模板库（甲方原版 · 全局复用）

- **公共公告模板库**：第1~17号公告正文模板，村/社区通用（社区 = 村民→居民、村→社区、乡镇→街道 自动替换称谓）
- 公告按日程阶段**自动预填充** → 小编/运营编辑点开**编辑内容**（公文格式实时预览）→ 确认发布 → 公告记录 + 小程序前端同步
- **管理员只改日期，其他基本不改，主打只做审批点手指**
- 公文格式（GB/T 9704）：标题2号小标宋居中、正文3号仿宋、首行缩进2字符、落款右对齐，布局排版不能错

### 12.5 角色权限（漏斗末端）

- 角色：超管 / 子管理 / 经办编辑 / 审核员 / 参选人
- 超管、子管理：可编辑+可审批；经办编辑：可编辑不可审批；审核员：可审批不可编辑；参选人：查看+提交材料
- **子管理不能创建角色**（角色创建超管才行）；子管理可删人员
- 角色切换演示：后台管理 → 角色管理 → 设为当前（localStorage 持久化）

### 12.6 材料提交（无选民 · 参选人）

- **无选民**！参选人 = 面向有资格参选的人（基层民主自荐 + 组织推荐后台导入）
- 自荐需材料审核通过后与候选人走一起；组织推荐（后台手工导入）不用材料审核
- 阶段可「开启材料提交」→ 用户端公告下显示提交按钮 → 上传材料进材料管理 → 归档历史归档本届文件夹
