# 村居换届选举系统 · 设计总纲（V1.0 落笔版）

## 一、系统定位（一句话）

**一套给基层选举内部人员用的换届官宣系统——登录进村，看日程，管理侧操作、参选人提交下载。**

- 不是给选民的，**无选民、无投票、无申诉**
- 系统角色 = 管理员工作台/指挥棒：日程+公告告诉管理员每个阶段该做什么、该发什么公告
- 傻瓜式：打开系统就知道今天该干嘛

## 二、复用铁律（最重要）

**每个村子都是这样，一个搞定，其他都搞定。**
所有村/社区 = 同一套系统/流程/页面/模板，差异只有：① 数据内容（org_id）② 村/社区类型（选举细节+岗位方式）。做好一个村 → 130+ 全部复用。禁止单独定制。

## 三、登录漏斗（防串台）

```
归属地（130+村/社区）→ 组织类型（村/社区）→ 账号（手机号+密码）→ 角色 → 进自己的村
```
缺一不可，不会串台。数据隔离 = org_id 强制过滤。

## 四、角色与权限

| 角色 | 定位 | 能力 |
|---|---|---|
| 参选人 | 前端展示 | **就三件事**：提交材料、下载公告、下载报名表。**没了** |
| 管理侧（超管/子管理/经办编辑） | 操作 | 六模块全功能 + 编辑/发布公告 + 看用户材料 + 审核 + 改候选人结果 |

**参选人无（前端隐藏按钮，不是置灰）**：编辑公告 / 确认发布 / 查看用户材料 / 编辑候选人结果。
**按日期隐藏**：日期没到的公告/通知，参选人看不到（藏起来）；未来预告仅管理侧可见。
**双保险**：前端不渲染按钮 + 后端接口二次校验。

## 五、前端（小程序蓝本 · 青墨鎏金克制版）

**管理侧六模块**：① 首页（换届进度一目了然）② 公告通知（三Tab+阶段分组+红头详情）③ 候选人公示（四轮审核轨迹）④ 材料提交（窗口自动开关）⑤ 选举流程/岗位（岗位清单+公告模板+花名册）⑥ 我的。

**参选人三件事**：材料提交 + 公告下载 + 报名表下载。

**风格标杆**：首页 + 公告通知列表。朴素稳重、信息优先、装饰克制、公文质感。**禁止**：hero 大渐变、光晕、夸张动画。

## 六、后端（PostgreSQL + Node/Express + JWT）

### 六大块
1. **数据层**：23 表已建（orgs/accounts/roles/elections/stage_templates/election_stages/positions/announcements/materials/candidates...）
2. **登录鉴权**：归属地+手机号+密码+角色 → JWT（带 org_id+role）→ 全查询 org_id 过滤
3. **日程引擎（发动机）**：输入 D+org_type → stage_templates 偏移 → 生成 election_stages 真实日期；改 D 全表平移
4. **公告按日期**：参选人只返回已到日期；管理侧看全部
5. **材料审核**：提交→审核→四轮公示（r1收审→r2资格→r3复核→r4确认，前置不过后续冻结）
6. **文件**：本地目录存储

### 参选人 API（仅三个）
`POST /api/materials`（提交）· `GET /api/announcements`（只已到日期）· `GET /api/positions`（岗位+报名表下载）

## 七、D-day 如何确定（提案审批 → 审核 → 确认）

**后台第一个模块 = 提案审批（选举申请）**，D-day 的源头。

```
编辑/经办/子管理 提交「选举申请方案」：
   ① 选举日期（D）
   ② 选举方式（村 / 居委会 选举方式有差别）★ 关键列
   ③ 岗位配置：岗位 + 人数（职数）+ 要求
   ④ 岗位报名表 / 资料表下载链接
  → 审核员审核
  → 驳回 = 不行（Dday 未确认，可修改重提）
  → 通过 = Dday 正式确认
  → 锁定：前端选举方式 + 后台选举岗位内容 同时确定
  → 进入 elections 表（D）+ positions 表（岗位/职数/要求）→ 日程引擎生成 16 阶段
通过的最新的提案 = 当前展示的选举活动
```

- 对应表：`proposals`（提案/选举申请，含选举方式/岗位配置与下载链接），`prop_status` = 活动通过/驳回
- **注意：村（村委会）与居委会（社区居委会）的选举方式有差别**，提案必须带「选举方式」列
- **提案通过 = 前端选举方式 + 后台选举岗位内容确定（锁定）**
- **只有审核通过的选举申请，才会进入选举活动**，D 与岗位配置才正式生效

## 八、核心引擎流程（日程 pipeline）

```
管理员输入 D（正式选举日，如 2026-10-30）
  → 读 stage_templates（16 阶段偏移量）
  → 自动生成 election_stages（每阶段真实日期）
  → 判定当前阶段（未到/进行中/已过）
  → 进行中 → 公告模板预填充 → 管理员确认 → 发布（官宣）
```

## 八点五、日程驱动执行原理（唯一时钟）

**日程是唯一的时钟，一切动作按 election_stages 日期自动执行，无人工开关。**

| 动作 | 由哪个阶段控制 |
|---|---|
| 自荐报名开放/关闭 | 提名/收审阶段（到点自动开/关） |
| 材料上传窗口 | 收审阶段（开放/截止自动，窗口条显示状态） |
| 审核时间 | 审核阶段 |
| 公告发布 | 跟随日程 → 提前提示 → 管理员确认发布 |

**管理员工作 = 跟着日程提示操作**（该发公告确认发，该审核就审），不手动开关任何窗口。

## 八点六、防遗忘提醒 + 近期预告（给工作人员敲钟）

- **提早通知 = 防遗忘**：管理员/工作人员怕忘记，系统在阶段开始前**提前提醒**"该做 X 了"（发公告、收材料、审核…）。公告自动提示的核心价值 = 给工作人员敲钟，不是给群众看的。
- **近期预告 = 还没开展的步骤**：前端公告通知页的「近期预告」Tab，把**未来未开展的日程步骤**列在那里，管理员一眼看到接下来要做什么。
- 预告对参选人**隐藏**（未来内容只管理侧可见），参选人只看到已到日期的公告。

## 十一、技术选型（一套真相 · 用户钦定）

**统一一套 UI 前端框架，一个真相，不搞多套。**

| 层 | 选型 | 说明 |
|---|---|---|
| UI 框架 | **TDesign** | Web + 小程序设计语言统一（小程序端已在用 t-* 组件） |
| Web 前端 | React + Vite + TDesign for React | 组件齐全（表格/表单/上传/弹窗） |
| 小程序 | 原生小程序 + TDesign | 已用 |
| 后端 | Node + Express | 轻量稳定 |
| 数据库 | PostgreSQL | 本地已跑通（23 表） |
| 富文本 | wangEditor | 补材料正文编辑（g5 缺失项） |
| 文件上传 | 本地存储 | 简单稳定 |

> 原则：借 g5 视觉思路，不借 AntD 组件；业务逻辑按认知全解重搭。
